# 项目状态汇报

人不改看板，只通过对话把事情交给你；汇报是你向人负责的方式。读者通常只有两分钟，所以先说他必须做的事。

## 步骤

1. 运行 `olav-tasks tasks digest <项目目录>`（想要结构化结果加 `--json`，陈旧阈值用 `--stale-days N`）。若输出先报“诊断”，先用 `tasks validate` 修好看板再汇报，在此之前不要报“就绪”和“关键路径”。
2. 读项目根目录的 `PROJECT.md`（如有）：目标、优先级原则、“完成”的定义，用它判断哪些风险重要。
3. 对 digest 里要写进结论的项做核实，不照抄状态：进行中的任务看实际改动或证据；声称完成的看任务正文里的验证记录；陈旧的任务问清是真的卡住了还是只是没更新状态。核实不了的写“未核实”。
4. 按这个顺序汇报，每段没有内容就省略：
   - **等你决定**：每条一句话说明选项和你的建议；对应任务应带 `blocked_by: "needs decision: …"`，缺了就补上。
   - **风险**：过期、陈旧、关键路径上的阻塞，各给出原因与你打算怎么办。
   - **进展**：本期完成了什么（带证据）、正在做什么（谁在做）、父任务进度。
   - **下一步**：就绪任务里你建议先做的 1 到 3 项，并说明为什么；用户同意再认领。
5. 汇报不是写入：不要借汇报改任务状态。需要改的，说明后在对话里照常处理（`tasks claim`、`tasks new`，改完 `tasks validate`）。

## 不要

- 把 digest 原样贴给用户；它是你的素材，不是成品。
- 把“进行中”当作“正在被人推进”：没有负责人或很久没有变化的，按风险报。
- 为了好看省略坏消息。
