# 项目规划

使用客户端现有文件工具完成规划，无需 Olav Tasks CLI、SDK 或其他 skill。

## 收敛范围

- 以用户选定项目为边界，按需读取项目协作规范、计划索引和相关任务。先搜索定位，再读相关段落；不遍历全文来凑背景。
- 说明要解决的问题、已有能力、本次交付和暂缓事项。区分已确认需求与建议；影响范围或验收的关键缺口才向用户提问，其余假设明确标注。
- 将任务拆到有独立可观察结果的粒度。每项写明目标、范围、验收条件及真实依赖；按用户价值、阻塞关系和成本排序，给出下一步。

## 记录任务

只要求讨论时在回复中给计划；要求落盘或更新 backlog 时写入所选项目。沿用已有目录、编号和索引格式，先查重并更新已有任务。

新增 Olav Tasks 看板任务使用以下 frontmatter；ID 沿用项目编号规则并保证唯一。优先级可省略，使用时说明理由。

```yaml
---
schema: olav.tasks/v1
id: TASK-001
title: "一项可验收的交付"
status: todo
priority: P1
assignee: agent:codex # 可选，仅有明确归属时设置
effort: M # 可选，仅有工作量依据时设置
model_profile: balanced # 可选，仅需 subagent 且项目有模型映射时设置
check: npm test # 可选，一条单行命令，退出码 0 表示机器可判定的验收通过
depends_on: []
---
```

`assignee` 可选，格式为 `human:<稳定ID>` 或 `agent:<稳定ID>`，例如 `human:alice`、`agent:codex`；ID 非空且不含空白或冒号。`effort` 可选，取 S/M/L，只描述工作量。仅在用户或项目上下文确切时设置，缺少依据就省略，不猜测或为旧任务批量补值。示例字段仅演示格式。

`model_profile` 可选，取 fast/balanced/deep，是 subagent 模型档位提示，不改变 assignee，也不由 effort 推算。只有需要派 subagent 且项目 `AGENTS.md` 有模型映射时才填写；派工先检查映射模型是否可用，未明确档位或非 subagent 工作沿用当前会话默认模型。

`check` 可选，单行 shell 命令（不超过 500 字符），由 Olav Tasks 服务端在任务运行的 worktree 里于每个 agent 回合后独立运行（目前只对此前版本创建的任务运行生效，页面已不能再启动任务运行），退出码 0 为通过；它只是证据，不会改变任务状态。只有验收条件确实能用命令判定时才写（例如测试、类型检查、`test -f`），主观或需要人判断的条件不要写成 check，也不要写"没有报错就算通过"这类弱检查。命令来自任务文件，不由 agent 修改。

正文写目标、范围和验收条件；依赖填真实任务 ID，未决问题写在正文。普通方案文档无需任务字段。新项目无约定时可用 `backlog/tasks/` 存任务、`BACKLOG.md` 存相对链接索引。

更新保留稳定 ID、已有状态、assignee、effort、model_profile、check、未知字段和无关正文；索引不重复维护任务状态。规划不代表开始执行或验收完成，不将任务改为 `in-progress` 或 `done`。任务状态由执行 Agent 根据真实进展维护；网页任务视图只读。既有其他任务格式保持原样，转成看板任务需包含在用户要求内。

不得擅自更换已有任务的负责人、工作量或模型档位；仅按用户明确要求或已确认项目依据修改，网页仍只读展示这些元数据。

结束时简述任务顺序、未决问题和实际修改的文件。实现工作另按用户要求及项目协作规范执行。

可选 `start_date`、`end_date` 仅在计划明确时写入真实 YYYY-MM-DD 日期，结束不得早于开始；不猜日期，缺少日期保持未排期。
